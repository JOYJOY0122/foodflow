# 食序 FoodFlow - Epic Breakdown

## Overview

本文件把 SRS v3.0（`prd.md`）與架構主幹拆成期中（11/18）首版的 epics 與 user stories。Epic 依 `docs/team-tasks.md` 的模組分工切分，每個 epic 只有一位負責人。

**範圍：**
- **納入：** SRS 第 7.1 節首版必做，即 FR-01～FR-18 與 NFR-01～NFR-08，NFR-07 除外。
- **不拆：** 第 7.2 節期末延伸項目，包含交易更正、FEFO 遵循率報表、外部通知、CSV 匯出；以及排在期末的 NFR-07 負載測試。
- **已完成：** 骨架、`seed-demo`、`verify-stock`、Idempotency-Key 解析、`FakeUnitOfWork`，以及帳號權限 FR-01、FR-02（PR #8）不再拆 story。
- **編號：** FR-16 是盤點調整（首版必做）；不拆的交易更正是 v2.0 的舊 FR-16，現列於第 7.2 節。

**每張 story 共通的完成定義（驗收條件不再重複）：**
- **權限：** 寫入 API 由路由層 `require_admin` 或 `get_current_employee` 把關，前端的角色判斷只影響顯示（AD-15）。
- **錯誤回饋：** 錯誤一律用 AD-16 格式，表單指出欄位並保留已填內容；未確認成功不顯示完成（NFR-05）。
- **快取：** 會影響庫存、預警或主檔的寫入成功後呼叫 `invalidateStockQueries()`（AD-18）。
- **介面：** 狀態用 `StatusBadge`；操作目標至少 44px、不依賴 hover。進貨、領用、報廢、預警頁在 1024×768 與 1366×768 檢查（NFR-01、AD-23）。
- **測試：** Service 單元測試用 fake Repository、`FakeStockLedger`、`FixedClock`；涉及列鎖、併發、防重送的寫入要有真實 PostgreSQL 整合測試。
- **交付：** 改 API 後重新產生並提交 `schema.d.ts`；CI 全綠；AI 使用記錄在 `docs/ai-log.md`。

## Requirements Inventory

### Functional Requirements

- **FR-01 登入與登出：** 員工以帳號密碼登入、登出；未登入不能取得營運資料。登入失敗不透露是帳號還是密碼錯；登出後原登入狀態不能繼續操作；直接存取無權限功能時，伺服器拒絕。
- **FR-02 員工帳號管理：** 管理者新增、修改、停用帳號，指派角色並重設密碼。帳號不得重複；最後一名有效管理者不能被停用或降權；停用帳號無法登入，既有登入的後續請求也被拒絕；停用不刪除歷史操作者。
- **FR-03 食材與分類管理：** 管理者新增、修改、停用分類與食材（名稱、分類、單位、保存方式、安全庫存量、啟用狀態）。名稱、分類、單位、保存方式必填；安全庫存量非負，未填為 0；名稱重複時提示；有庫存或歷史交易的食材不能刪除或改單位；停用食材不能新增進貨，既有庫存仍可領用、報廢、查詢；有啟用食材的分類不可停用；單一單位、最多三位小數（A2）。
- **FR-04 供應商管理：** 管理者維護名稱、聯絡人、電話、其他聯絡資訊與狀態。名稱必填且至少一種聯絡方式；有進貨紀錄的供應商不可刪除；停用供應商不能用於新進貨，歷史單據仍可查。
- **FR-05 儲存位置管理：** 管理者維護位置代碼、名稱、儲存類型與說明。代碼唯一，名稱與類型必填；進貨只能選有效位置；有剩餘庫存的位置不能停用；整批換位置須由管理者登記原因，保留前後位置與時間，數量與到期日不變（A3）。
- **FR-06 建立進貨單與確認入庫：** 員工建立草稿（供應商、進貨日期、一筆以上明細：數量、單價、到期日、位置），確認後每筆明細建立唯一批次與進貨異動。草稿不增加庫存；同一食材不同到期日或位置須分開明細；數量大於 0、單價非負可選填、進貨日期不晚於今天、到期日不早於進貨日或確認當天；整張單全部成功或全部不生效，重複確認不重複入庫；單價保存在明細與批次；到期日必填，缺效期只能留草稿（A4）。
- **FR-07 查詢與沖銷進貨：** 員工依日期、供應商、食材、單號查詢進貨；批次可追查原進貨單、明細與供應商。已確認進貨不可覆寫或刪除；尚無後續異動的進貨可由管理者整單沖銷並填原因；有後續異動的批次禁止沖銷，以盤點調整處理。
- **FR-08 查詢庫存總覽：** 員工依名稱、分類、保存方式、位置、狀態（正常、即期、今日到期、過期、低庫存）搜尋食材。分開顯示實體量、可用量、過期量、安全庫存量；篩選位置時只合計該位置批次並標示條件；不同食材、不同單位不合併。
- **FR-09 查看批次與異動：** 員工展開食材批次，看批號、來源、進貨日期、到期日、位置、初始量、剩餘量、狀態。批次分別呈現並可依到期日排序；可連到來源進貨與相關異動；已耗盡批次保留歷史，但不計入可用量與待處理預警。
- **FR-10 FEFO 領用建議：** 員工選食材與數量後，系統列出未過期且有剩餘的批次，較早到期者優先，並建議各批扣量。同到期日依進貨日期、批號排序；最早批次不足時自動往下一批建議；顯示位置與可用量；可改選其他可用批次，但偏離建議須填原因並標記「非 FEFO」；過期與零庫存批次不能領用；需求量大於可用量時拒絕並顯示目前可用量。
- **FR-11 登記領用與扣庫存：** 員工確認一筆以上批次與數量後扣庫存並記錄異動。數量大於 0 且不超過提交當下剩餘量；多批次全部成功或全部不生效，每個被扣批次各一筆領用異動；兩人同時領用不能超領，失敗者收到最新可用量；人工登記消耗（A5）。
- **FR-12 即期、今日到期與過期提醒：** 依第 5 節規則分類仍有剩餘量的批次。清單含食材、批號、位置、數量、單位、到期日、剩餘天數；三種狀態互斥、不重複計數；用完或全數報廢的批次移出待處理預警；過期不自動扣庫存。
- **FR-13 低庫存提醒：** 可用量 ≤ 安全庫存量時，在首頁與庫存總覽提醒。顯示食材名稱、可用量、安全量、缺口量；過期量不計入可用量；進貨、領用、報廢、盤點後同步更新，補貨高於安全量即解除；安全量為 0 不提醒。
- **FR-14 預警首頁與設定：** 登入後首頁即預警首頁，依過期 → 今日到期 → 即期 → 低庫存排序，可依狀態與位置篩選，並連到領用、報廢、建立進貨單；管理者設定全店預警天數。過期批次不能經預警連結領用；預警天數只接受非負整數，更新後新查詢套用；載入、重新整理、操作成功後依最新數量與當日日期更新並顯示更新時間；只做站內預警（A6）。
- **FR-15 報廢登記：** 員工選批次，登記報廢量與原因，確認後扣庫存並建立報廢紀錄。原因為過期、變質、損壞、其他（其他須補說明）；報廢量大於 0 且不超過剩餘量；同時建立報廢紀錄與異動，保留操作者、時間、原因、損失金額（報廢量 × 批次單價，無單價記為未知）；過期預警可一鍵報廢該批次剩餘量，原因預設「過期」；全數報廢後剩餘量為 0，歷史仍可查。
- **FR-16 盤點調整：** 管理者輸入批次實際盤點量與原因，系統顯示帳面量與差額，確認後產生調整異動。實際量不能小於 0；無差額不新增異動；預覽後被他人改過庫存時拒絕舊確認並要求重新核對；確認後可追查調整前後數量與原因。
- **FR-17 查詢庫存異動：** 員工依日期、食材、批次、類型、操作者查詢異動。顯示時間、操作者、來源單據、批次、增減量、前後量、原因、是否非 FEFO；沖銷可追查原紀錄；位置變更與數量異動分開呈現；異動不可修改或刪除。
- **FR-18 庫存與報廢統計：** 員工依日期區間看各食材期初、進貨、領用、報廢、調整、期末量；管理者依食材、分類、原因看報廢數量與損失金額分布。期初＋淨進貨－淨領用－淨報廢＋調整淨額＝期末；沖銷於確認當日反映並歸入對應項目；報廢統計可展開明細、不同單位分開、金額只加總有單價者並標示未知筆數。

**共用商業規則（SRS 第 5 節，所有 story 適用）：**
- **數量：** 批次不得為負；超過三位小數明確拒絕，不靜默截斷。
- **日期：** 以 Asia/Taipei 當日計算，D＝到期日－今天、T＝預警天數：D＜0 過期、D＝0 今日到期、1≤D≤T 即期、D＞T 正常；T＝0 無即期。預設 T＝3，今日到期仍可領用，次日禁止（A7）。
- **低庫存：** 可用量 ≤ 安全量且安全量 > 0。
- **交易：** 同次提交全部成功或全部不生效，重試不重複。
- **資料保留：** 被引用主檔不得刪除，已確認交易以沖銷或盤點更正。
- **統計時間：** 按確認時間，起日 00:00 含、迄日次日 00:00 不含。

### NonFunctional Requirements

- **NFR-01 裝置與易用性：** 繁體中文 Web，1024×768 平板橫向與 1366×768 電腦可完成進貨、領用、報廢、預警查詢；關鍵操作可觸控、不依賴 hover；狀態同時用文字與顏色。
- **NFR-02 資料一致性：** 同批次多人操作、重複提交或操作中斷，不產生負庫存、重複異動或半套資料。
- **NFR-03 可追溯性：** 所有數量變動有操作者、時間、來源；可由有效異動重算目前量；位置變更保留歷史。
- **NFR-04 安全與權限：** 密碼以適合的雜湊儲存；權限在伺服器端驗證；對外部署用 HTTPS（期中只在本機與區網，HTTPS 延後）。
- **NFR-05 錯誤回饋：** 指出缺漏或錯誤欄位並保留已填內容；未確認成功不得顯示完成。
- **NFR-06 資料保存：** 重啟後成功紀錄仍在；提供備份與還原程序，並核對還原後批次與異動一致。
- **NFR-07 效能：** 排在期末，本次不拆。
- **NFR-08 可維護性：** 設計層次 4；批次挑選、預警規則、通知方式以 Strategy、Factory、Adapter 隔離，新增預警規則或通知方式只需新增類別。

### Additional Requirements

以下為架構主幹中會影響 story 切分與驗收的技術要求。

**跨模組共通（每個 story 都要遵守）：**
- **AD-1、AD-2 分層與注入：** router → service → repository 介面，具體類別只在 `dependencies.py` 組裝；import-linter 在 CI 檢查。
- **AD-3 實體與載入：** relationship 一律 `lazy="raise"`，需要的關聯由 Repository 以 `selectinload` 載入。
- **AD-4 資料表擁有權：** 每張表只有一個寫入模組；跨模組只能用 `StockLedger` 與 `get_current_employee`、`require_admin`。
- **AD-5、AD-20 庫存寫入：** 所有庫存變動經 `StockLedger`。
- **AD-6、AD-7 交易與列鎖：** 交易邊界在 Service；鎖定順序固定，處理順序為取鎖 → 防重送檢查 → 其他檢查。
- **AD-8 防重送：** 確認入庫與沖銷用狀態機；領用與報廢用 `Idempotency-Key`；盤點用 `expected_quantity`。
- **AD-9 數量與金額：** 數量與金額以字串傳遞，最多三位小數，`Decimal` 運算。
- **AD-10 時間：** 只用 `Clock`；跨日以 `FixedClock`、`APP_FIXED_NOW` 測試。
- **AD-16 API 與錯誤：** `/api/v1` 前綴、統一錯誤格式；前端型別由 OpenAPI 產生並提交 `schema.d.ts`。
- **AD-17、AD-18 前端資料：** 元件只透過 `features/<f>/hooks.ts` 取資料；庫存相關 mutation 成功後呼叫 `invalidateStockQueries()`。
- **AD-23 介面：** `StatusBadge` 同時顯示文字與顏色；操作目標至少 44px；進貨、領用、報廢、預警頁的 PR 要在 1024×768 與 1366×768 檢查。
- **測試慣例：** Service 單元測試用 fake Repository、`FakeStockLedger`、`FixedClock`；列鎖、併發、防重送的測試連真實 PostgreSQL。

**模組專屬：**
- **AD-11 效期狀態：** 唯一來源為 `classify_expiry`、`is_available`；SQL 篩選要有對照測試。
- **AD-12 批次挑選：** `BatchSelectionStrategy`，以 `FefoStrategy`、`ManualStrategy` 實作；`POST /issues/suggestions` 不上鎖，`POST /issues` 在鎖內重算基準並判定 `is_non_fefo`。
- **AD-13、AD-14 預警：** `AlertRule` 四個規則與 `AlertRuleFactory`；預警即時計算、不存表；`InAppNotifier`；回應帶 `generated_at`。
- **AD-15 認證：** JWT 放在 httpOnly cookie，以 `token_version` 撤銷，`create-admin` 建立第一位管理者。
- **AD-21 庫存量與低庫存：** 唯一來源為 `stock_level_stmt`、`is_low_stock`；低庫存以全店可用量判定；停用食材不提醒低庫存。
- **AD-22 統計：** 數量只來自異動，依 `occurred_at`；`REVERSAL` 歸入原類型；報廢金額來自 `waste_record`，限管理者看。

**部署與維運：**
- **NFR-06 備份還原：** `scripts/backup.sh`、`restore.sh`，還原後執行 `verify-stock` 並比對批次與異動筆數。
- **C5 驗收：** 在 `APP_FIXED_NOW` 下可登入並完成一次寫入。
- **整合：** 11/11 走通「進貨 → 領用 → 預警 → 報廢」，並以 SRS 第 9 節端到端示例驗收。

**已完成，不拆 story：**

- **工具：** `seed-demo`、`verify-stock`。

- **帳號權限（PR #8）：** FR-01、FR-02、AD-15，包含登入登出、員工管理、`create-admin`、前端登入頁與員工頁。

## Epic List

**切分原則：**
- **負責人：** 依 `docs/team-tasks.md` 的模組切分，每個 epic 一位負責人，story 不跨人。
- **完整功能：** 每張 story 包含後端 API 與對應的前端頁面，由同一人從頭做到尾。
- **編號順序：** 依相依關係排列，相依只指向前面的 epic；不代表時程，各 epic 可平行開發。
- **預警排在報廢之後：** Epic 7 的一鍵報廢依 AD-23 使用 Epic 6 匯出的 hook，所以排在後面。預警清單、低庫存與設定不需要等 Epic 6。

### Epic 1: 食材、分類與供應商

**負責人：** 謝文佳（`master_data` 模組，分支 `feat/master-data`）

管理者建立與維護進貨要選用的食材（含安全庫存量）、分類與供應商；員工可查詢。被引用的資料只能停用，歷史保留。

**FRs covered:** FR-03、FR-04

### Epic 2: 儲存位置與整批換位置

**負責人：** Ken（`storage_location` 模組，分支 `feat/storage-location`）

**FRs covered:** FR-05
